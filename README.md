# ИСВО — главная страница

Отдельная рабочая основа сайта в `Code/isvo-site`. Реализованы Hero,
секция направлений техники с прямыми ссылками на модели, три раздела каталога,
12 страниц техники, раздел «Индивидуальный проект», боковая навигация, мобильная шапка, общий подвал и окно контактов. Три предыдущих прототипа
в `Code/ISVO Website Redesign*` не изменены.

Стек: **Astro 7.3.5, TypeScript 5.9.3, Tailwind CSS 4.3.3**, Vite внутри Astro.
Основа взята из локального проекта «Фотограф Тюркан-Мария»: структура `app/`,
файловая маршрутизация и статическая сборка. Вся разметка генерируется в HTML;
меню и нативные диалоги управляются небольшим TypeScript-скриптом. React и его
гидратация удалены: для текущего интерфейса они не нужны. Framer Motion также
не используется. На хостинге достаточно раздавать `dist/`.

## Запуск

Из папки `Code/isvo-site` сайт запускается через `Makefile`, как в проекте
«Фотограф Тюркан-Мария»:

```sh
make
```

`make` (или `make dev`) устанавливает зависимости, если отсутствует
`node_modules`, и запускает сайт на http://127.0.0.1:4321/.
Если порт занят, Astro выбирает следующий свободный и выводит адрес в терминале.
При наличии встроенного Node.js Codex используется он; иначе — Node.js из `PATH`.
Перед запуском проверяется минимальная версия Node.js 22.19.0 (нужна Lighthouse).

Команды из `Code/isvo-site`:

| Команда | Действие |
| --- | --- |
| `make install` | Установка зависимостей через `npm ci --include=dev` |
| `make check` | Проверка Astro и TypeScript |
| `make build` | Статическая сборка в `dist/` |
| `make preview` | Просмотр готовой сборки |
| `make audit` | Сборка и мобильный Lighthouse; нужен установленный Chrome/Chromium |
| `make audit-desktop` | Сборка и десктопный Lighthouse |
| `make release` | Чистая установка зависимостей, проверка и сборка; без публикации |

Прямой запуск из `Code/isvo-site` через npm также доступен.
Нужен Node.js **22.19+**. В `.nvmrc` указан 22.22.0.

```sh
nvm use
npm ci
npm run dev
```

Адрес: http://127.0.0.1:4321/.

```sh
npm run check
npm run build
npm run preview
```

В навигации используется `@lucide/astro`: `ArrowUpRight`, `ArrowRight`, `Menu`
и `X` импортируются по отдельным путям `@lucide/astro/icons/...`. При сборке
Astro вставляет только используемые SVG непосредственно в HTML; библиотека
не добавляет клиентский JavaScript, иконочный шрифт или запросы за иконками.
Размеры SVG заданы явно, цвет наследуется через `currentColor`, декоративные
иконки скрыты от скринридеров. Исходные иконки преимуществ Hero сохранены.

Мобильное меню плавно выезжает справа и уходит обратно при закрытии, одновременно
меняется затемнение фона. Движение задаётся CSS; скрипт дожидается
завершения закрытия, сохраняя модальность и блокировку прокрутки. При переходе
к контактам или на десктоп меню закрывается сразу. `prefers-reduced-motion`
отключает анимацию. При открытии фокус получает кнопка закрытия, поэтому вокруг
логотипа нет автоматической рамки; клавиатурный индикатор фокуса сохранён.

## Адаптивная навигация

- От 1200 px — постоянная боковая панель шириной 268 px; в контактах только
  телефон, без отдельной почты и кнопки «Получить предложение».
- На 768–1199 px — верхняя шапка высотой от 192 px: логотип, телефон и CTA
  в первом ряду, компактные ссылки по ширине текста по центру второго ряда. Активный пункт
  выделен полностью скруглённой подложкой высотой 32 px с лёгкой внутренней
  тенью без рамки. Область нажатия остаётся высотой 44 px.
- До 768 px — компактная шапка высотой от 76 px с логотипом без подписи,
  прямой ссылкой «Техника» и подписанной кнопкой «Меню».

Боковая панель и горизонтальная шапка используют одну разметку
`SiteNavigation.astro`, `NavigationLinks.astro` и `NavigationContacts.astro`.
Пункт «Техника» для обеих шапок берётся из `equipmentNavigation` в
`app/content/site.ts`; в каталоге он отмечен как текущий раздел.
Подписи «Скоро» сохранены у недоступных страниц.

`VineDivider.astro` отделяет верхний ряд шапки от горизонтального меню
только на 768–1199 px. В боковой панели и мобильном меню лозы нет.
Лоза занимает всю ширину окна; логотип, контакты и меню остаются внутри
боковых полей сетки. Над первым рядом — 32 px, до и после лозы — по 16 px.
Высота разделителя — 28 px; на 840 px узора приходится десять листьев четырёх
форм: резной, овальный, узкий и небольшой молодой лист.
Бесшовный `pattern` использует `userSpaceOnUse`, поэтому при изменении ширины
видна большая или меньшая часть узора, а размер листьев и толщина стебля
сохраняются. Середина узора привязана к центру окна: при сужении он обрезается
с обеих сторон. Цвет берётся из фирменного зелёного; декоративный SVG скрыт
от скринридеров, не перехватывает нажатия и не требует JavaScript.

Ниже 1200 px основной контент занимает всю ширину окна. `sizes` изображений
Hero, направлений и карточки товара учитывают отсутствие боковой панели.
Высота Hero учитывает верхнюю шапку через `--site-header-height`.
При переходе с телефона на среднюю ширину открытое меню закрывается;
фокус переносится на видимый пункт навигации. Возврат из окна контактов
также учитывает смену компоновки во время открытия диалога.

## Фотография и референс

### Направления техники

`EquipmentDirections.astro` задаёт композицию главной: крупная уборка слева,
посев справа сверху, горизонтальная защита растений снизу. На планшете уборка
занимает всю строку, фотография и текст располагаются рядом: верхняя навигация
оставляет карточке всю доступную ширину. На телефоне
порядок соответствует циклу работ: посев, защита, уборка. Он совпадает с порядком
HTML и чтения скринридером. На 320–374 px узкая карточка защиты тоже становится
вертикальной. На широких телефонах характер горизонтальной карточки сохранён.

- `app/content/equipment.ts` — типизированные направления, тексты,
  локальные фотографии, их фокус и функция формирования адресов разделов.
- `app/content/products.ts` — единый список моделей для главной, разделов
  и страниц техники. Главная показывает все 12 моделей:
  три для посева, две для ухода и семь для уборки. Названия и назначение
  редактируются в одном месте. Пути страниц генерируются из направления и `slug`.
- `app/components/EquipmentDirectionCard.astro` — карточка с вариантами
  `stacked`, `split`, `featured`. Внутри — независимые ссылки на модели с коротким
  назначением. Все модели доступны сразу; отдельной ссылки «Вся техника раздела»
  нет. У карточки нет перекрывающей ссылки
  поверх содержимого. Ссылки доступны с клавиатуры, имеют область нажатия
  не менее 44 px по высоте и работают без JavaScript.
- `app/components/EquipmentDirections.astro` — заголовок, описание и сетка.
  Выбирает варианты и `sizes`, учитывающие боковую панель, отступы и ширину фото.
- `app/globals.css` — общие токены отступов, заголовков, радиуса,
  длительности переходов и фокуса. Кнопки и переключатели направлений используют
  `--radius-leaf-control` (16 px), крупные карточки направлений —
  `--radius-leaf-card` (32 px): верхний левый и нижний правый углы скруглены,
  верхний правый и нижний левый остаются острыми, как у фирменного знака.
  Фотографии обрезаются по внешнему контуру карточки. Обычные строки моделей
  сохраняют небольшой симметричный радиус `--radius-small`.

Землистый терракотовый `--color-terracotta: #75513f` используется как локальный
фон варианта `split` (защита растений) на всех размерах экрана. Белый текст
и белый индикатор фокуса сохраняют контраст. Основной светлый фон, зелёный
фирменный цвет и жёлтый цвет основных действий сохраняют свои роли.

Посев и культиватор используют существующие `hero-seeding.jpg` и
`hero-cultivator.jpg`: источники указаны в таблице ниже. Новый кадр уборки —
`Каталог/Уборка урожая/Навесной овощеуборочный транспортер/НОУТ-18/DJI_0074.JPG`.
Его полная копия без кадрирования уменьшена до 2400×1600 px и сохранена в
`app/assets/equipment/harvesting-nout-18.jpg`; оригинал не изменён.

Astro создаёт AVIF 45 / WebP 76 в размерах 320, 480, 640, 800, 1280, 1920 px
без увеличения исходников. Совпадающие варианты фотографий Hero переиспользуются.
У всех трёх изображений есть `width`, `height`, `srcset`, `sizes`, `loading="lazy"`,
`decoding="async"`, низкий приоритет загрузки и содержательные `alt`.
Секция не добавляет клиентского JavaScript. Подсветка и подчёркивание при
наведении относятся к конкретной модели; `prefers-reduced-motion` отключает переходы.

Кнопка Hero «Подобрать технику» и пункт меню «Техника» ведут к
`#equipment-selector`. Оба работают и без JavaScript. После каталога размещён
блок «Индивидуальный проект» со ссылкой на отдельную страницу.
Внешний вид Hero и концепция навигации сохранены;
остальные будущие страницы остаются недоступными.

### Страницы техники

Разделы `/catalog/seeding/`, `/catalog/crop-care/`, `/catalog/harvesting/`
перечисляют все модели соответствующего направления. Страницы моделей имеют
адрес `/catalog/<направление>/<slug>/`: описание, основные характеристики,
особенности, контакты и другую технику направления. Кнопка запроса открывает
письмо с названием модели в теме. На страницах каталога в меню выделяется «Техника».
Маршруты статически генерируются из тех же данных, что и ссылки на главной.

Точный относительный путь исходного листа хранится в поле `source` каждой модели.
Недатированные сведения о наличии, ценах и сроках изготовления не перенесены.
Для МКР-144 и НОУТ-1 отдельные фотографии пока не подключены; шаблон показывает
текст и характеристики без пустого места под изображение.

### Индивидуальный проект

`/individual-project/` описывает разработку по техническому заданию заказчика:
согласование требований → эскиз → проектирование и изготовление → проверка
и передача готового решения. На странице также есть список исходных данных
для первого обращения. Сроки, стоимость и состав работ согласуются по проекту.

Ссылка добавлена в общую навигацию и подвал. Главная использует отдельный
компонент `IndividualProjectTeaser.astro`. Адрес и название раздела находятся
в `individualProjectNavigation`, почта с темой «Индивидуальный проект — ИСВО» —
в `contact.projectEmailHref` (`app/content/site.ts`). Кнопка «Обсудить проект»
ведёт к контактному блоку, «Отправить ТЗ» открывает почтовый клиент.
Новая форма, серверный обработчик и дополнительный JavaScript не добавлены;
переходы и контакты работают без JavaScript.

Фотография `app/assets/individual-project-manufacturing.jpg` — уменьшенная
до 1600 px копия `Фото/Производство/IMG_20160926_140234.jpg` относительно
корня рабочего пространства. Оригинал сохранён. Astro создаёт AVIF/WebP
шириной 400, 640, 960 и 1440 px; фотография загружается только в новом разделе.
`sizes` учитывает масштабирование горизонтального исходника по высоте
вертикального кадра на десктопе.

Страница и переход с главной проверены в Chromium и WebKit на ширинах
320, 390, 768, 1024, 1200, 1440 и 1920 px. Проверены активный пункт меню,
переходы по якорям, тема письма, закрытие мобильного меню, режим без JavaScript
и отсутствие горизонтальной прокрутки. `make check` и `make build` прошли.
Скриншоты и результаты находятся в `outputs/individual-project/`.

## Заявка

В старом прототипе форма показывала успех по таймеру без отправки данных.
Здесь все CTA используют один обработчик и событие `isvo:inquiry`.
До подключения формы открывается доступный нативный диалог с телефоном и email.

Окно контактов и мобильное меню используют общий фон: затемнение 46% и размытие

анимируются только прозрачность и положение. Общие стили находятся в
`app/components/navigation.css`, направление задаётся через `--dialog-offset`.
До завершения закрытия сохраняются нативная модальность и блокировка прокрутки.
Escape, крестик и клик по фону используют один обработчик. При
`prefers-reduced-motion` переходы окна и фона отключаются, закрытие мгновенное.

```ts

  // Открыть реальную форму, передав event.detail.source и event.detail.intent.
});
```

`detail.intent`: `proposal` или `selection`.
`detail.source`: `hero`, `sidebar`, `navigation`, `footer` или `hero-selector`.
Для полноценной отправки нужны интерфейс формы и рабочая интеграция с сервером/CRM.
Обработчик ответа должен показывать успех только после подтверждённой отправки.
Секреты интеграции нельзя размещать в статическом клиентском коде.

## Настройка опубликованного сайта (933944.ru)

Проверка 03.11.2026: Nginx 1.24.0 (Ubuntu), HTTP/2 и gzip уже работают.
HTML получает `Cache-Control: no-cache`, но изображения и шрифты — только
7 дней (`604800` секунд). В ответе два `Cache-Control` с повторяющимся
`max-age`: вероятно, одновременно настроены `expires` и `add_header`.
Для прохождения [проверки Lighthouse](https://developer.chrome.com/docs/performance/insights/cache)
нужен срок минимум 30 дней. Увеличивать его для всех файлов без разбора нельзя:
неверсионированные ресурсы могут остаться у посетителей после обновления сайта.

После текущей сборки фотографии, используемый логотип и оба шрифта имеют
хеш содержимого в `/assets/`. Для них подходит годовой кеш с `immutable`.
HTML, favicon и остальные файлы с постоянными адресами должны проходить
перепроверку через `no-cache` (файл может храниться в кеше, ответ `304` допустим).
Не кладите файлы с постоянными именами вручную в `public/assets/`.

Фрагмент `deploy/nginx-static.conf` предназначен для существующего HTTPS-блока
`server`, у которого `root` указывает на опубликованную сборку. В нём:

- `/assets/`: один `Cache-Control: public, max-age=31536000, immutable`;
- HTML и файлы без хеша: `Cache-Control: no-cache`;
- gzip для HTML, CSS, JavaScript, SVG и текста; AVIF/WebP/WOFF2 уже сжаты;
- неизвестные пути: `404`; нет подмены отсутствующих файлов главной страницей.

При проверке публичный `/robots.txt` возвращал HTML главной с кодом `200`,
поэтому SEO в мобильном Lighthouse составил 92. В исходниках корректный
`public/robots.txt` уже есть: его нужно опубликовать вместе с остальной сборкой.

Порядок применения на сервере:

1. Собрать проект через `make release` и загрузить содержимое `dist/`, включая
   `robots.txt`. Новые файлы `assets/` загрузить перед HTML; сохранить старые
   файлы с хешами для уже открытых страниц, в том числе их отложенной галереи.
   Не использовать удаление всех предыдущих `assets/` при каждом обновлении.
2. Сохранить копию текущей конфигурации. Перенести правила из фрагмента в
   HTTPS-блок, заменив старые `location`/правила кеша и сжатия. Не добавлять
   второй одинаковый `location` и убрать старую регулярную обработку статики,
   которая могла бы переопределить новые правила. `root`, сертификаты и HTTP/2
   оставить настроенными для текущего сервера. В `http` должен быть подключён
   стандартный `mime.types` с AVIF, WebP, SVG и WOFF2.
3. Если есть общие security-заголовки через `add_header`, сохранить их и в
   новых `location`: в Nginx 1.24 локальный `add_header` отменяет наследование
   этих директив. Это [правило Nginx](https://nginx.org/en/docs/http/ngx_http_headers_module.html).
4. Выполнить `sudo nginx -t`. Только при успешной проверке —
   `sudo systemctl reload nginx`.

После применения проверить реальный URL любого нового файла с хешем из HTML:

```sh
curl -I https://933944.ru/
curl -I https://933944.ru/assets/ИМЯ_ФАЙЛА_ИЗ_НОВОЙ_СБОРКИ
curl -sS -D - https://933944.ru/robots.txt
curl -I https://933944.ru/this-page-does-not-exist
curl -sS -D - -o /dev/null -H 'Accept-Encoding: gzip' https://933944.ru/
```

Ожидаются соответственно `no-cache`; годовой кеш; текст robots с кодом `200`;
`404`; `Content-Encoding: gzip` и `Vary: Accept-Encoding`.
Затем повторить Lighthouse по публичному адресу с очищенным кешем.
Обычный `make audit` намеренно не имитирует серверный кеш и сжатие: это
отдельная проверка страницы. Результаты текущих проверок — `outputs/cache-delivery/`.
Конфигурация подготовлена локально; на публичном сервере автоматически не применялась.

Локальное сравнение до/после в одинаковом мобильном профиле без gzip и кеша:
Performance 99 → 100, LCP 2,10 → 1,81 с, первый кадр 79,2 → 45,3 КиБ
(800 px/AVIF 50 → 640 px/AVIF 45). Предупреждение `Network dependency tree`
исчезло после предзагрузки второго шрифта. Оценка лишнего объёма изображений
снизилась с 63 до 29 КиБ, но проверка `Improve image delivery` пока отмечена.
Не следует уменьшать разрешение под одну оценку Lighthouse в ущерб экранам
с высокой плотностью пикселей. Это единичные лабораторные прогоны, не гарантия
таких же времён на сервере. Отдельный замер текущей публичной версии до изменений:
Performance 100, LCP 1,64 с; усиление сервера по этим данным не требуется.

`make check` и сборка прошли. В браузере проверены 320, 390, 768 и 1440 px:
геометрия не изменилась, оба шрифта загружаются по одному разу, меню и диалог
работают, ошибок загрузки нет; WebP-fallback проверен отдельно. Логотип в сборке
побайтово совпадает с исходным. `nginx -t` нужно выполнить на целевом сервере.
